# 字段口径

## 目标：就绪延迟

作业被调度到机器上之后，还要过一段时间才进入就绪状态。这段时间就是**就绪延迟**——
资源已经分配给它，但它还不能开始计算。

| 字段 | 含义 | 建模时 |
|---|---|---|
| `ready_status` | 该次执行最终是否进入就绪状态 | 用于筛选队列，不作为特征 |
| `ready_delay_sec` | 就绪延迟（秒） | **预测目标**，不得进特征矩阵 |

有两个口径需要说明：

- **未就绪的作业**把 `ready_delay_sec` 一律记为 `-1`。
- **已经就绪的作业里，也有一小部分**记为 `-1`（它们的平均声明时长远长于总体，属于超长作业，
  并非随机缺失）。把它们当零延迟会系统性低估等待，直接丢弃又会引入选择偏差。

因此本仓库的建模队列只取 `ready_status == 1 且 ready_delay_sec >= 0` 的记录；
上述那一小部分单独报告，不并入队列。`exp60_caliber` 会把两边的行数都落成 JSON。

训练目标取 `log1p(ready_delay_sec)`：延迟跨越五个数量级，取对数压缩跨度，同时不改变排序。

## 执行摘要表（逐作业一条记录）

| 字段 | 含义 | 建模时 |
|---|---|---|
| `server_id` | 落点机器 | **按此分组切分**，不作为特征 |
| `gpu_spec_public` | 加速器机型（请求侧） | 特征（L0） |
| `priority_class` | 优先级类别 | 特征（L0） |
| `job_type_public` | 作业类型 | 特征（L0） |
| `model_type_public` | 模型类型 | 特征（L0） |
| `is_genai_request` | 是否生成式请求 | 特征（L0） |
| `gpu_request` | 请求的 GPU 数（可为分数） | 特征（L0） |
| `duration_hours` | 声明时长（小时） | 特征（L0） |
| `schedule_delay_sec` | 调度延迟（秒）：提交到被调度的时长 | 特征（L1） |
| `server_req_count` | 见下 | 特征（L1） |

九项属性按**取值时刻**分成两层：

- **L0（7 项）**：作业提交时就能拿到。
- **L1（2 项）**：在队列与调度环节才产生。

这一分层用来做一组对照，回答"只用提交时可得的信息还剩多少预测能力"——见
`exp62_models` 里 `l0` 与 `lgb` 两行。

### 一个派生量

| 字段 | 含义 |
|---|---|
| `server_req_count` | 同一 `server_id` 在**建模样本内**出现的次数。由样本内生计数得到，不是原始字段；换抽样比例会变，跨样本比较时要注意。 |

## 分层抽样与切分

- 抽样按 `server_id` 做 5% 的**机器分组**抽样（`exp61_sample`）：同一台机器的全部行一起进或一起出。
- 切分同样按 `server_id` 分组五折（`exp62_models`）：一台机器不会同时出现在训练与验证两侧。

两处都这样做的原因相同：同一台机器上的作业共享机器状态，随机划分会让模型"记住"某台机器
的固有快慢，从而拿到虚高的表面性能。

## 供给侧表（逐服务器小时）

逐服务器小时表按 `day=/hour=/part-*.parquet` 组织。本仓库用到四列：

| 字段 | 含义 |
|---|---|
| `server_id` | 机器标识 |
| `gpu_count` | 该机器持有的 GPU 卡数 |
| `gpu_spec_public` | 机型 |
| `asw_id` | 机架标识（只在观测期后段可见） |

`exp70_supply` 由它产出 `out/fleet_census.parquet`，并补一个派生标记：

| 字段 | 含义 |
|---|---|
| `in_ref_day` | 该机器在参照日是否在线 |

## 容量单位

装箱引擎把容量统一换成整数：**1 张卡 = 100 个容量单位**
（`delay_aware_scheduling/fleet/constants.py` 的 `SCALE`）。请求卡数同样按这个刻度取值
（请求 1 张卡记 100、4 张记 400），全部用整数比较，避免浮点边界抖动。请求规模分档的切点
见同一个文件里的 `SC_BINS`。
